# Orchestrator path

Orient and enroll your own bounded coordination assignment as a worker first. Keep
the distinction between the integration effort and its individual implementation
owners. Completed assessments do not authorize the implementation they assessed.

Reconstruct the current picture from the provider's durable records, timestamped
snapshot, locally observed sessions and source/evidence references. Identify actual
dependencies, inconsistent assumptions, current revision comparisons and concrete
next gates. Shared semantic boundaries can merit integration even with no file
overlap. Do not manufacture convergence, invariant changes or reviewer findings.

## Provider reconciliation

Routine recording of an already user-assigned task belongs to the worker's configured
`task-register` capability; see the source's `docs/TASK_REGISTRATION.md`. A human or
separate coordinator need not create every task. Reconciliation remains appropriate
for conflicting metadata, missing capability or unresolved uncertain provider writes.

Use supported `provider-list` and `reconcile` commands only through configured,
authorized provider access. Read `docs/REPORTING.md` and each command's help. Inventory
native issues before creating assignments: the snapshot contains only the enrolled
subset. Preserve native identities, declared owners, exact reference checkouts,
relationships, exclusions and independent readiness dimensions. Compare the current
metadata digest before applying a correction; re-inspect on disagreement.

If you lack authorized publication access, leave an exact enrollment/correction
packet and identify the publishing boundary. Do not scavenge admin credentials or
use direct database writes. A worker confirmation improves enrollment fidelity; it
does not independently verify its implementation evidence. Publish durable reports
using `publish-report` and reconcile uncertain results rather than blindly retrying.

## Dispatch and continuity

The current optional local session connector is a provisional coordination tool.
Read `docs/SESSION_CONNECTOR.md` and its installed command help before attachment or
continuation. A known session UUID is a reference; establish the supported attachment
to the existing assignment and checkout before sending work. Keep request identity,
bounded scope and delivery receipt so retrying a request does not duplicate work.
Successful queue delivery does not mean the worker is running or the work succeeded.

When the user authorizes direct agents or another execution tool, use it within the
assignment and keep Project Intent enrollment/reporting explicit. Direct dispatch is
not yet a SparkOps admission receipt. Do not claim an automatically managed session
or continuous monitoring that the actual tool has not established.

Delegate bounded follow-up to the existing owner with intent, paths/seams, applicable
revisions, acceptance, environment and expected evidence. Continue routine inspection,
coordination and verification under the existing objective. When an external decision
is required, present the concrete next action and evidence so the human can decide
once; do not make the human carry routine CLI commands or worker reports.

Obtain independent review of the exact delivered source, route specific findings to
their owners, and reverify corrections before handoff. A reviewer should perform a
real review task, not a synthetic lifecycle scenario. Report blocked dependencies and
which gates remain before merge or production. End with the supported reporting
workflow and release presence when paused or complete.

The mature SparkOps execution-consumer bridge is deferred. It will own admission,
environment selection, credentials, spawn/resume and execution receipts. Project
Intent remains independently available and Mission Control remains read-only now.
