## Question and boundaries

Can Sol Medium use frozen PI reliably, then preserve integration while several
competent workers implement substantial, independently owned components?
Use `gpt-5.6-sol`, `model_reasoning_effort="medium"`, native Codex 0.153.4.
Record native turn-context identity; a requested model is not proof it ran.
Native JSON recording follows the [Codex documentation](https://learn.chatgpt.com/docs/non-interactive-mode).
No model downgrade, production activation, PI repair, or automatic publication.

PI is frozen from main `689a91979e313ac295e2e9277d82b4c9d0dff573`, behavior
v0.05. Backend and worker instructions get separate source hashes. Trial workers
receive only its backend, skill and operational documents, never historical results.
The installed production wrapper may be older; trials use the exact frozen CLI.

## Gate 1: protocol competence, not software efficacy

Nine planned fresh sessions: three repetitions of each scenario, sequential order
audit, repair-owner, repair-peer, repeated three times. Maximum 300 seconds/session.
Each has a fresh committed disposable repository, native profile and PI feed.

- **Audit:** select the real consumer assignment among distractors; enroll the
  actual session/checkout; inspect a semantic peer and a stale passing declaration;
  run the actual producer/consumer probe; report the failing integrated state and
  release without editing the excluded product files.
- **Repair owner:** volunteer to repair a specific consumer break with a named
  simulated peer who could otherwise make the same edit. After enrollment, that
  peer changes its producer from dollars to cents and updates real PI presence.
  Obtain explicit agreement before editing, fix the tiny adapter, check the actual
  combined source, complete the plan, retain a handoff and release.
- **Repair peer:** the simulated peer proposes the same bounded repair after the
  worker's actual session exists. Inspect and acknowledge the plan, avoid editing
  its consumer path, refresh after the peer's real fix, validate the combined
  source, retain a handoff and release. Never treat a passing peer summary alone
  as acceptance.

The deterministic peer is explicitly a calibration actor, not another model. It
uses the same frozen PI CLI, acts only for its own synthetic session and implements
the preregistered state transitions. Its actions are logged separately. These
scripted exercises measure ability to operate a protocol when explicitly asked;
they do not establish spontaneous protocol use or benefit in software work.
Each completed session requires a source/hash-bound observer review before the
next session can launch; that review cannot message or repair the finished worker.
There are no evaluator messages or retries. Actor failures are infrastructure
failures, not model failures, and stop the batch for investigation.

Record observable endpoints, not a subjective coordination score: correct native
identity, scoped discovery, enrollment, actual probe execution, post-change context
read, repair agreement/closure where applicable, report, release, and exclusions.
Command output proves information was exposed, not that it influenced reasoning;
review logs before attributing understanding or causality. Retain recovered errors.

Proceed only with at least 8/9 fully passing scenarios, at least 2/3 per family,
and no authority/exclusion violation. Stop early if the same protocol endpoint
fails twice, if an exclusion is violated, or if infrastructure is invalid. Preserve
unlaunched scenarios as not run. This is a bounded gate, not a population estimate.
Do not repair PI/instructions to pass it. If it fails, publish the exact observation
and stop before the distributed software experiment.

Protocol v1 was frozen and passed six deterministic checks but **launched no model**.
Independent prelaunch review found a stale-probe timing false positive, missing
native-profile hash enforcement, and a missing temporal-exclusion review interlock.
Version 2 fixes those recorder/scorer issues before inference; PI is unchanged.

## Gates 2–3: distributed fixture and ordinary calibration

Only after Gate 1 passes: design the smallest substantial synthetic product with
four independently owned component roots in one repository. This respects current
PI repair's same-repository scope; it does not claim cross-host/multi-repo repair.
Candidate components: catalog/inventory, order checkout, settlement/outbox, and
reporting/legacy receipts. Difficulty must come from API/data migrations, precision,
compatibility, persisted versioning, delayed events, replay/idempotency and shared
integration—not obscure algorithms or deliberately slow work.

Before model execution, test a reference implementation and deliberate contract
mutations against the acceptance checker. Keep reference/evaluator material out
of worker mounts. Component-local tests must be distinct from product acceptance.
All task facts, architecture and acceptance requirements are available to B and C.

Cap ordinary calibration at two explicitly versioned fixture candidates, three
concurrent projects per candidate and two single-worker ceiling checks for the
selected candidate. Target an unsaturated ordinary baseline (roughly 30–70%, not
a significance test). If all pass, increase distributed difficulty within that
cap, never weaken Sol. If all fail, inspect whether the fixture is reasonable.
Do not silently select successes, retry errors or pool calibration with evaluation.
If the bounded calibration cannot establish a reasonable region, report that
instead of starting a falsely calibrated treatment comparison.

## Gate 4: frozen software evaluation

After calibration, freeze final fixture, checker, prompts, PI, recorder, model and
worker count. Three fresh single-worker A projects; five ordinary B and five PI C
projects. B/C share four bounded component roles; no orchestrator or self-allocation.
One project at a time; workers within B/C launch concurrently. Proposed fixed order:
A1, B1, C1, C2, B2, A2, B3, C3, C4, B4, A3, B5, C5.
Maximum 900 seconds per worker/project execution window; no imposed repair phase.
No worker follow-ups, revision broadcasts, supplied peer notes, correction rounds
or integration successor. Workers retain ordinary shell/Git/tests and may naturally
coordinate or repair within their task authority. Do not manufacture concurrency.

Primary endpoint: accepted integrated project under the frozen checker. Report
focused checks separately. Passive source history and native event streams support
post-run first-accepted-state replay, source retention, duplicate/stale work counts
and measured timelines. Replay is sampled, not an atomic filesystem journal.
Separate setup, first accepted project time, final worker exit, verification,
aggregate worker-seconds, token subsets and PI operations/overhead. Never call a
quick failed project cheaper than an accepted project without that qualification.

Classify failures conservatively: coding, stale contract, conflicting edits,
missing integration, decomposition, PI misuse, missing/stale PI information,
infrastructure or ambiguous. PI observations are not proof of causal impact.
